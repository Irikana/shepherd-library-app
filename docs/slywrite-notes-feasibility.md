## 一、结论先行

| 问题 | 结论 |
|------|------|
| 技术上能否把 SlyWrite 变成通用 Markdown 笔记软件？ | **能，且成本不高**。当前架构已经是「编辑器 + 远端仓库」两层，缺的是一层 **存储提供者抽象**（Provider）和「本地优先」的笔记库模型 |
| 登录时选「图书馆管理 / 笔记撰写」是否合理？ | **合理，但不要把 GitHub Token 作为笔记模式的门票**。笔记模式应当零账号可用，图书馆/发布模式才要 Token |
| 能否上架各大应用商店？ | **Google Play 可以（有 2 个必须先改的阻断项）；App Store 可以但要付年费并补 2 个强制能力；国内安卓商店短期不建议**（软著 + 备案 + 内容审核责任，投入产出差） |
| 能否靠它牟利？ | **能挣到钱，但挣不了大钱**（第一年现实区间：个人开发者净收入 数千 ~ 3 万元人民币量级）。真正决定上限的是「GitHub 仓库即笔记后端 + 一键出版级发布」这条差异化能不能被看见 |
| 最大的风险是什么？ | 不是技术，是**同质化 + 独立开发者的持续维护负担**（Markdown 笔记赛道极度拥挤，Obsidian / 思源 / Joplin / flomo / Typora / 备忘录类都在） |

建议路线：**先 Play 免费上架做「双模式」，Pro 功能用本地一次性解锁 + GitHub Releases 分发做对照实验；数据好看再上 iOS + IAP；国内商店等有成再说。**

## 二、现有代码的契合度盘点（我读到的事实）

### 2.1 已经具备的（比你想的更接近笔记软件）

| 能力 | 现有实现 | 笔记模式可复用度 |
|------|----------|------------------|
| Markdown 编辑器（工具栏 / 数学符号面板 / 脚注 / 站点视觉组件片段） | `src/components/MarkdownEditor.tsx`（ACTIONS / SYMBOL_GROUPS，插入按钮 `onPressIn` 避开输入法） | 90%，只需去掉「站点视觉组件」那一组换成笔记向片段（表格、任务列表、callout、代码块、双链） |
| HTML ↔ Markdown 双向还原 | `src/lib/html-to-markdown.ts`（turndown，站点结构化类名原样保留）+ `src/lib/article-parser.ts`（marked 渲染回写） | 60%；笔记模式根本不需要还原 HTML，但「把已有网页/文章转成笔记」是杀手功能（今天已验证 8 个真实页面往返零结构损失） |
| 草稿与本地持久化 | `src/store/drafts-store.ts`（AsyncStorage，防抖 600ms，只存真实改动，撤销回默认自动清理） | 80%，改造成「笔记自动保存」即可 |
| 元数据 / 标签体系 | `slywrite-config.json` 的 tags + 本次新增 tagColors；`MetaForm` / `EditMetaForm` / `TagChips` | 85%，笔记模式需要再加「笔记属性」（类型、状态、收藏），标签颜色直接复用 |
| 仓库文件浏览 + 在线编辑 + 新建 | `app/browser.tsx`（逐层 GitHub Contents API）+ `app/editor.tsx`（元数据 / 正文 / 源码三页，本次再加「内容页面」模式） | 70%，这就是「远端笔记本」的雏形 |
| 图片选择与上传 | `expo-image-picker` + base64 PUT | 90%，笔记附件同一套 |
| 认证与令牌存储 | `src/lib/auth*.ts` + `expo-secure-store`（本次未改） | Token 存 SecureStore 是对的，符合商店要求 |
| 主题（11 套 App 色板 + 明暗） | `src/theme.ts` / `settings-store.ts` | 100% |
| 应用内更新 | `app/updates.tsx` + Releases 下载 APK | **Play 版必须移除**（见 4.1） |
| 内置更新日志 + 时间条 | `app/changelog.tsx`（本次新增滑动时间条） | 100% |

### 2.2 明显缺失的（笔记软件的最小要件）

1. **没有「笔记库（Vault）」概念**：现在所有读写都写死指向「站点仓库」——`src/lib/config.ts` + `config-store` 里的 repo/branch。要有 `Workspace` 抽象：`{ id, kind: 'github' | 'local', root, displayName }`，支持多工作区与切换。
2. **没有本地文件系统访问**：依赖 `expo-file-system`，但 UI 层没有任何「本地目录」概念。笔记模式需要 `expo-document-picker`（选文件夹）或 SAF（Android）/ `expo-file-system` 的 scoped 目录（iOS 沙盒内），并处理「用户清数据=笔记消失」的备份责任问题。
3. **没有本地全文索引与双链**：现在全文检索是网站侧 `js/library-dynamic.js` 的 `Search.data`。笔记模式需要本地倒排/模糊索引（纯 JS 就够：分词 + Map，万条以内毫无压力）+ `[[wiki 链接]]` 解析。
4. **没有冲突处理**：GitHub PUT 靠 sha 乐观锁，失败提示重试。笔记多端（手机 + 电脑 Git）会出现真冲突，需要「拉取 → 三方合并 → 提示」或至少「保留两个版本」。
5. **没有导出/分享**：Markdown → PDF / 图片卡片 / 剪贴板，是笔记软件的高频付费点。
6. **没有搜索替换、批量操作、回收站、版本历史 UI**（版本历史其实**已经免费躺在 GitHub commit 里**——这是个非常好的卖点，只差一层界面）。
7. **没有账号/付费体系**：Entitlement 需要本地记录 +（跨设备时）服务端校验。

工作量判断：1-3 是笔记模式 MVP（约 4-8 周兼职），4-7 是「能用」到「愿意付钱」的距离（再 4-8 周）。

## 三、建议的产品与技术方案

### 3.1 双模式：在登录页分叉，之后仍可切换

```
启动 → 工作区选择页
  ├─ A. 图书馆 / 发布模式（现状全部能力）→ 需要 GitHub Token（fine-grained，仅 Contents 读写，限定目标仓库）
  └─ B. 笔记模式（默认落地页）→ 无需任何账号，本机即用
        └─ 可选增强：绑定 GitHub 仓库做同步 / 绑定站点做一键发布（此时才要 Token）
```

要点：
- **入口顺序反过来了**：现在的 App 打开就是登录页（Token 门槛）。开放给普通用户时，「不注册也能写笔记」是底线，否则转化会被直接打死。GitHub Token 是极客专属，不能当门神。
- 工作区模型落地下拉：`app/_layout.tsx` 根据 `workspace-store`（新增）决定路由守卫；设置页加「工作区管理」。
- 代码层重构最小切口：把 `src/lib/github-client.ts` 提为 `GithubProvider implements ContentProvider`，新增 `LocalProvider`；上层（browser/editor/compose）只依赖接口（`list/get/put/delete/search`）。这是**唯一必须做的架构改动**，其余都是加页面。
- 笔记模式的数据格式：**直接就是 `.md` 文件 + YAML front-matter**（title/tags/created/updated/status），与 Obsidian/Joplin 互通，用户不怕被锁——这条对口碑极其重要。

### 3.2 差异化定位（别做「又一个 Markdown 编辑器」）

你手里有三张别人没有的牌：

1. **GitHub 即免费后端 + 免费版本历史**：不打自家云，用户拥有仓库，冲突和回滚都靠 commit。竞品要么收费同步（Obsidian Sync / flomo）、要么自建云（思源）。
2. **写作即可发布**：同一篇笔记 → 网站文章 / 新闻卡片 / 知识馆词条（`templates/article.ts` 已经会生成合规 HTML、插 `library.html`、写搜索数据）。这是「个人知识 → 公开出版物」的一条完整管道，中文市场几乎没有对手做到端到端。
3. **出版级中文排版**：站点 alpha-021 的主题/字体/首行缩进/标题层级体系，可以原样搬进 App 的预览与 PDF 导出，「写出来的东西像书」比「支持 GFM」更打动人。

一句话定位建议：**「写给未来的自己出版：Markdown 笔记 + GitHub 存档 + 一键成为你的图书馆」**。

## 四、上架的硬门槛（逐条列，含必须先改的代码）

### 4.1 Google Play（优先，成本最低）

| 事项 | 说明 | 现状 |
|------|------|------|
| 账号费用 | 一次性 $25；个人开发者账号需完成身份验证 | 需注册 |
| **新账号测试要求** | 新个人开发者账号通常需**封闭测试 ≥12 名测试者连续 14 天** + 达到留存门槛才能转正式（需联网核对 "Pre-launch testing requirements"） | 提前 2-4 周准备测试群（图书馆读者群正好用） |
| **应用内自更新 = 违规** | `app/updates.tsx` 下载并安装 APK（`REQUEST_INSTALL_PACKAGES`）违反 Play 的「不得绕开分发机制更新应用」条款，且该权限属受限权限，**上架包必须移除该模块与权限**，改用 Play 内置更新（In-App Updates API） | 需要「Play flavor」：编译期或运行期 `Constants.appOwnership`/`BuildConfig` 判断隐藏该功能。**GitHub Releases 渠道保留自更新**（侧载合法） |
| 打包形式 | 必须 **AAB**（不是 APK）、目标 API 等级要求（Android 15 门槛逐年上抬）、Play App Signing | 现在 CI 产 release APK，需加 `bundleRelease` + AAB 上传步骤（Expo prebuild + gradle 即可，不必用 EAS） |
| 数据安全表单 | 声明收集/共享的数据类型；纯本地+用户自己的 GitHub 仓库 → 可声明极简 | 要写清「Token 只存本机 SecureStore，内容写进你自己的仓库，我们不持有」——这是极强的隐私卖点 |
| 隐私政策 URL | 必须有（英文 + 中文，GitHub Pages 上放一页即可） | 待写；我可以顺手用图书馆模板生成 |
| **账号删除要求** | 若提供账号登录（GitHub Token 算），需**在应用内或网页提供账号删除途径**（Play 2024 起强制，需核对） | GitHub 侧无我方账号，说明页 + 清除本机数据按钮即可满足，但要写清 |
| 内容分级问卷 / 目标受众 | 不含 UGC 浏览、非儿童向 → 简单 | 保持「不内置他人内容浏览」的定位，分级最轻 |

### 4.2 Apple App Store（第二批）

| 事项 | 说明 |
|------|------|
| 费用 | $99/年（个人/公司均可） |
| 第三方登录规则（4.8） | 提供 GitHub 登录就必须同时提供 **Sign in with Apple**（付费 SDK，需 Apple 开发者账号）。笔记模式「无账号可用」正好规避大量审核摩擦 |
| 内购（3.1.1） | 数字内容/订阅收费**必须走 IAP**，不能引导外部支付（引导去官网付款解锁 Pro 会 3.1.1 拒审）。用 `react-native-iap` 或 RevenueCat |
| 审核常见驳回 | 纯 WebView 壳 / 功能过少 / 无离线能力 / 崩溃。Expo prebuild 原生壳 + 离线可用，这两条都稳 |
| 自更新提示 | iOS 不能诱导去外部更新，只能提示「去 App Store 更新」 |
| 隐私标签 | 与 Play 表单同口径 |

### 4.3 国内安卓商店（华为 / 小米 / OPPO / vivo / 应用宝）—— **建议暂缓**

1. **软著证书**：几乎所有国内商店要求《计算机软件著作权登记证书》。自行申请免费但周期 30-40 个工作日，加急代办数百至上千元。
2. **备案 / 域名**：应用若关联服务端与域名，多数渠道要求 ICP 备案；`irikana.github.io` 在境外托管，无法备案 → 需自有域名 + 备案主体（个人备案不得涉及经营性内容）。
3. **实名 + 对公资料**：部分渠道要求企业主体；个人开发者可上架但模板审核更严。
4. **内容审核责任**：一旦用户可用你的 App「发布内容到公网」，你在国内会被期待承担内容安全义务（关键词过滤、举报入口、日志留存）。**规避办法**：发布目标永远是**用户自己的仓库/站点**，App 只是本地工具，不做「平台侧内容展示」——把这条写进用户协议与隐私政策，并在架构上确实不留平台侧入口（现在就是这样）。
5. 收益现实：国内商店分发要面对「换机助手搬运工」环境，工具类 App 的搜索流量极弱，投入产出比最差。

## 五、变现方案与现实预期

### 5.1 定价结构建议

- **免费层**：笔记模式全部基础能力（本地 + GitHub 同步 + 编辑器 + 主题 + 版本历史浏览）——把「同步」留在免费，是对 Obsidian 付费墙的正面进攻点。
- **Pro 买断（建议 ¥38 ~ ¥68，Play 一次性内购）**：多工作区、PDF/图片卡片导出、双链图谱、自定义发布模板、批量替换、App 端主题包。
- **Pro 订阅（¥6 ~ ¥12/月）** —— **暂不做**，除非你愿意承担服务端成本与合规（那是另一门生意）。
- **主题/模板包**（¥6 ~ ¥18 单卖）：alpha-021 的六套配色 + 免版权字体方案天然可拆成「出版物主题包」，这是你已有产能、别人难复制的 SKU。
- 图书馆站点 / GitHub 仓库继续免费，作为**展厅与获客漏斗**（站点页脚 → 下载 App）。

### 5.2 收入现实（按可验证的量级估，不吹）

工具类中文独立 App 的典型漏斗：

| 阶段 | 累计下载 | 付费率 | 客单 | 收入 |
|------|---------|--------|------|------|
| 上架 3 个月（无私投，靠站点/论坛/V2EX/即刻） | 1k ~ 5k | 2% ~ 4% | ¥45 | ¥900 ~ ¥9k |
| 一年内（有 1-2 次外部推荐/榜单） | 10k ~ 30k | 2% ~ 3% | ¥45 | ¥9k ~ ¥40k |
| 悲观（无流量、同质化压死） | <1k | 1% | ¥45 | <¥500 |

扣掉：Play $25（一次性）、Apple $99/年、商店抽成 15%（小规模计划）~30%、软著/域名备案杂费。**第一年现实预期是「把咖啡钱和服务器钱挣回来」，不是「以此谋生」。** 若目标是谋生，必须做订阅或面向 B 端（写作营/课程配套工具），那是另一个规划。

### 5.3 非金钱收益（别忽略）

- 你自己的图书馆站点会被反哺（更多文章、更快更新）；
- 一个可展示的工程作品集（求职/接单时比任何简历都有说服力）；
- 中文独立开发者社区能见度；
- 「用户的数据在用户自己的 GitHub 仓库」这件事本身有价值观层面的口碑回报。

## 六、风险清单与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| GitHub 是境外服务，国内访问不稳 | 用户同步失败 → 差评 | ① 笔记模式本地优先、同步异步可排队；② 失败明确提示「网络/代理」而非报错栈；③ 长期考虑支持 Gitee / 任意 WebDAV / S3 兼容 Provider（Provider 抽象后成本很低） |
| Token 权限过大（用户误给 repo/workflow 写权限） | 安全事故 | 登录页内置「fine-grained PAT 创建指引 + 权限清单」，并检测 Token 权限范围过大时警告 |
| 用户清 App 数据 / 换机丢笔记（纯本地模式） | 信任崩塌 | 强制引导「本地 + 至少一个远端 Provider」；导出 zip 一键备份；首次使用就提示风险 |
| 应用内自更新被判违规 | Play 下架 | 见 4.1：分渠道构建，Play 版彻底移除 |
| HTML↔Markdown 往返细节丢失（复杂页面） | 内容损坏 | 已做类名保留规则并跑过 8 页面验证；再加「保存前 diff 预览 + 原文快照 commit」双保险 |
| 站点数据结构被 App 写坏（历史事故：撇号打瘫全站） | 你的主站瘫痪 | 已确立：任何写站点文件前 `node --check`；再加 App 侧「写入前语法自检 + 失败不落库」 |
| 单人维护不过来（双端 + 三渠道 + 服务端） | 长期烂尾 | 明确不做：协同编辑、评论、云端账号、平台内容分发。技术栈保持 Expo 单码 |
| 合规灰色地带：用户用它向公网发布内容 | 内容责任 | 协议写明「工具不托管、不展示、不筛选内容，发布目标为用户自有仓库」，App 内不含他人内容浏览入口 |
